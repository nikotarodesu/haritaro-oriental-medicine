## Stripeの追加改善
- Checkoutの前に、会員とStripe顧客IDをサーバー管理のapp_metadataに保存。保存失敗時は支払画面を作らない。以前の契約の顧客IDも引き継ぐ。
- 未完了の決済画面は再利用。既存契約・別プランの未完了申し込みは409で停止。5分ごとに新しい申し込みを作る方式を廃止し、直前の決済履歴を基に重複リクエストをまとめる。
- このサイトの料金IDも検証。同額の別商品への支払いでは権限を付与しない。
- 顧客IDの不一致、古い契約からの更新、テスト・本番のWebhook取り違えを検出。他サイトの契約は会員更新せず受信完了とする。
- Stripeキー未設定は署名エラー400ではなく設定エラー503を返し、再送対象にする。
- 決済から戻った画面では確定待ちを最大30秒間自動で再確認。確定しない場合は再申し込みを促さず再確認・問い合わせに案内。

### 設定確認の方法
`npm run check:billing` は環境変数の設定有無だけを確認。
`npm run check:billing -- --remote` はその環境のキーで料金・Webhook・契約管理設定を読み取り確認する。作成・更新・決済は行わず、秘密キー・顧客情報は出力しない。
`--production` を追加すると本番キーかどうかも確認する。ローカル診断結果をVercel本番の診断結果と混同しないこと。
プレビュー宛先の診断にはBILLING_CHECK_WEBHOOK_URLにその環境のWebhook URLを指定する。権限反映失敗のログはイベントIDと種類だけを出力し、顧客情報やキーを記録しない。
キーはVercelのSensitive環境変数で管理し、必要な権限だけの制限付きキーを優先する。
税込表示に対応する価格のtax_behaviorと税務上の扱いを確認する。Stripe Taxを使用する場合は登録状況を確認してから設定し、自動では有効化しない。

### 公開前の決済受け入れ確認（テスト環境）
1. 同じSupabaseプロジェクトの管理キーをサーバーに設定したテスト用プレビューを用意する。Stripeも同じSandbox／テスト環境の料金・キー・Webhookを揃える。
2. Googleで本人としてログインし、月額・年額をそれぞれテスト決済。初回請求書paidとサーバーの会員権限を確認。
3. 連打・別タブ・決済中断・5分以上経って再試行しても、顧客と有効な契約が増えないことを確認。
4. 追加認証・失敗カード・Webhook遅延／再送・更新失敗を確認。失敗時に権限を付与しないことを確認。
5. 契約管理で支払方法変更・期間末解約を行い、満了まで権限が残り、満了後に終了することを確認。
6. 上記の証跡を残してから本番設定を照合し販売開始。モックの回帰テスト合格のみでは販売可能と判断しない。

### 残る制約
Stripe側の履歴とidempotencyは通常の連打・再試行を防ぐが、データベースの一意制約や排他制御の代替ではない。顧客・契約・イベントの専用テーブル、Webhook処理記録と権限更新のトランザクション化、返金・異議申し立て時の権限方針は今後の改善項目。
現在はapp_metadataを更新するため、異なるWebhookの同時実行の完全な直列化は保証していない。接続できているSupabase管理先がサイトと異なるので、管理先を一致させてから専用テーブルへ移行する。
